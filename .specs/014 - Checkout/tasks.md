# Tasks: Spec 014 - Checkout com Mercado Pago e Acesso por Módulo

Spec full-stack. No `api/` (NestJS + Prisma + Jest) a suíte de testes vem **antes** da implementação, conforme `.claude/RULES.md`; no `front/` (Angular standalone + signals + Tailwind) valem o Design System da Spec 002 e os componentes de `front/src/app/shared/ui/`. As decisões referenciadas abaixo estão no `context.md`.

Ordem das fases: o modelo (preço, pedido, acesso) vem primeiro porque tudo depende dele; o `AccessService` vem antes do gateway, para que o portão de conteúdo possa ser fechado e testado sem um pagamento existir; o Mercado Pago entra depois, já tendo onde gravar o desfecho; e o front só começa quando a API cria pedido e concede acesso.

- [ ] **Task 1.1:** Escrever a suíte do `AccessService`: acesso ativo (`expiresAt` no futuro), acesso expirado tratado como ausente, concessão nova gravando `paidAt + 6 meses` de calendário, concessão sobre acesso **ativo** somando 6 meses ao que resta, concessão sobre acesso **expirado** recomeçando de agora, e concessão repetida do mesmo pedido sendo idempotente (decisões 4, 5 e 13).
- [ ] **Task 1.2:** Acrescentar `priceCents Int?` ao model `Module` do `api/prisma/schema.prisma`, documentando no comentário que nulo significa "a definir" e torna o módulo não vendável (decisão 1).
- [ ] **Task 1.3:** Acrescentar os models `Order`, `OrderItem` e `ModuleAccess` e os enums `OrderStatus`, `PaymentMethodKind` e `AccessSource`, com `@@unique([userId, moduleId])` em `ModuleAccess`, índice em `Order.userId`, índice único em `Order.mpOrderId`, `mpPaymentId` opcional e `onDelete: Restrict` de `OrderItem` para `Module` — módulo já vendido não é removível, pelo mesmo motivo que módulo já certificado não é (Spec 012, decisão 15).
- [ ] **Task 1.4:** Escrever a migration correspondente, com os dois backfills: `priceCents = 19900` (R$ 199,00) em todos os módulos existentes, valor temporário da decisão 1 — o default da coluna continua nulo, para módulo novo não herdar preço —, e uma linha de `ModuleAccess` com `source = LEGACY` e 6 meses a partir de agora para cada par (usuário existente × módulo existente), conforme a decisão 20.
- [ ] **Task 1.5:** Implementar o `AccessService` com `activeFor(userId)`, `hasActive(userId, moduleId)`, `grant(...)` e `revokeByOrder(orderId)`, expondo também o mapa de acesso por módulo que a trilha vai precisar — uma consulta por requisição, nunca uma por módulo.
- [ ] **Task 1.6:** Rodar `npm test` no `api/` e conferir que nenhuma suíte de `content`, `progress` ou `certificates` regrediu com as colunas novas.

## Fase 3: Backend - Mercado Pago / Orders API (TDD)
- [ ] **Task 3.0:** Ler a Referência de API de criação de order (`POST /v1/orders`) e fixar em `payments.types.ts` os nomes exatos dos campos que o checklist de qualidade exige e que a Orders API não herda de `/v1/payments`: emissor do cartão, identificador de dispositivo e descritor de fatura (decisão 15). Esta task existe para que as suítes seguintes assertem o payload certo, e não um payload inventado de memória.
- [ ] **Task 3.1:** Instalar o SDK oficial (`mercadopago`) no `api/` e criar `config/payments.config.ts` lendo `MP_ACCESS_TOKEN`, `MP_PUBLIC_KEY` e `MP_WEBHOOK_SECRET`, no padrão de `media.config.ts` — ausente fora de produção cai em modo desligado; ausente em produção impede a API de subir (decisões 16 e 24).
- [ ] **Task 3.2:** Escrever a suíte do `MercadoPagoService` com a rede dublada, sobre `POST /v1/orders` com `type: "online"` e `processing_mode: "automatic"`: order de PIX com `payment_method` `{ id: "pix", type: "bank_transfer" }` e `expiration_time: "PT30M"`, devolvendo `qr_code`, `qr_code_base64` e `ticket_url`; order de cartão com `payment_method` `{ type: "credit_card", id, token, installments }`; `X-Idempotency-Key` igual ao id do pedido; e `external_reference`, `items` e `payer` completo presentes no corpo (decisões 10, 13 e 15).
- [ ] **Task 3.3:** Escrever a suíte da validação de assinatura: manifesto `id:<data.id>;request-id:<x-request-id>;ts:<ts>;` conferido por HMAC com comparação em tempo constante, assinatura adulterada recusada, header ausente ou malformado recusado e `ts` fora da janela de tolerância recusado (decisão 12).
- [ ] **Task 3.4:** Implementar o `MercadoPagoService` — criar order, consultar order por id (`GET /v1/orders/:id`) e validar assinatura —, com a conversão centavos ↔ string decimal em um único ponto (decisão 3) e nenhum dado de cartão em log.
- [ ] **Task 3.5:** Escrever a suíte da tradução de status conforme a tabela do `context.md`: `created`/`processing`/`action_required` → `PENDING`, `processed` → `PAID`, `failed` → `REJECTED`, `canceled` → `CANCELLED`, `expired` → `EXPIRED`, `refunded`/`charged_back` → `REFUNDED` com revogação do acesso do pedido (decisão 22); `status` desconhecido tratado como pendente, e nunca como aprovado; `status_detail` preservado cru para a mensagem ao comprador.
- [ ] **Task 3.6:** Atualizar o `api/.env.example` com as variáveis novas, explicando em comentário por que a `public_key` sai pela API e não por build do front (decisão 16), que o webhook do tópico `order` é configurado na aplicação e não por requisição (decisão 7) e que ele exige URL pública em HTTPS (decisão 14).
